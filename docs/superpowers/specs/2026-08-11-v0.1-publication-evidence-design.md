# v0.1 Publication Evidence 設計

## 決策

v0.1 採 evidence-first 路線：先修正 OCI environment identity 與雙人 blinded
adjudication contract，再執行新的 current-contract reference suite。只有所有 publication
gates 都有可追溯 evidence 時，才請 owner 分別核准 OCI upload、GitHub Release 與 Zenodo
publication。

本階段的目標是把 BugSeed v0.1 從 methodology preview 提升為可正式引用、但仍不做
model ranking 的 benchmark release。Corpus 擴張與多 model 比較屬於 v0.2，另行設計。

## 為什麼不能直接執行新 run

目前有兩個會讓新 evidence 失效的 contract gap：

1. `prepared_image_digest` 實際比對 Docker local image ID，也就是 OCI config digest；它不等於
   registry manifest digest，無法作為第三方可 `docker pull` 的 immutable reference。
2. Formal ledger 對每個 `(fixture_version, bug_id, finding_hash)` 只允許一筆 ruling。第二位
   independent adjudicator 無法在不碰撞的情況下留下自己的 decision，也沒有 disagreement
   resolution 的資料模型。

若先執行 run，OCI re-pin 會改變 environment fingerprint 與 fixture version，使該 run 與後續
adjudication 失去 publication eligibility。因此順序必須是 environment contract、adjudication
contract、reference suite、human review、release audit。

## 範圍

### 本階段包含

- 把 OCI registry manifest digest 與 Docker config digest 分開記錄及驗證。
- 將兩個 fixtures re-pin 至公開、anonymous-pullable、`linux/amd64` 的 GHCR artifacts。
- 提供兩位 human reviewers 的獨立 blinded workflow，以及只在 disagreement 時啟動的第三位
  human resolver workflow。
- 執行一個 pre-registered、固定 model/configuration、涵蓋 v0.1 全部 10 tasks 的
  current-contract reference suite。
- 產生一份 complete、strict-replayable、independently adjudicated 的 reference result。
- 擴充 release audit，使任何缺少 OCI、trace、cost、latency、coverage、resolution 或 contributor
  provenance 的 release fail closed。

### 本階段不包含

- 不擴充 fixture、mutation、language 或 defect category。
- 不建立 leaderboard、model ranking 或 per-category capability claim。
- 不把 historical traces 回填成 current-contract evidence。
- 不由 AI、script 或 model 填寫任何 formal decision 或 rationale。
- 不新增 retry/backoff、dashboard、nightly sweep 或 model-as-judge。
- 未經 owner 單獨授權，不呼叫 paid provider、不 push OCI、不建立 GitHub Release、不上傳
  Zenodo。

## 不可破壞的 invariants

1. 原始 development checkout 的使用者修改與歷史不得 reset、覆寫或 rewrite。
2. `ledger/adjudications.jsonl` 的兩筆 owner rulings 保持 byte-for-byte、append-only；它們被標示為
   legacy single-review evidence，不遷移、不重算、不冒充 dual review。
3. 公開 Git lineage 的 author 與 committer 只能是
   `kuotunyu <61350295+kuotunyu@users.noreply.github.com>`，commit message 不帶 co-author trailer。
4. Private raw evidence、API keys、worksheet keymaps 不得進入 Git、OCI、Release 或 Zenodo。
5. Environment 或 finding bytes 改變時，舊 adjudication 不得自動繼承。
6. 任一不完整狀態只能產生明確 blocker，不得產生近似或部分 headline metric。

## Architecture A：OCI environment identity

### Manifest fields

Current fixture manifests 移除語意模糊的 `prepared_image_digest`，改用以下欄位：

- `prepared_image_repository`：公開 repository；固定為
  `ghcr.io/kuotunyu/coding-agent-eval-fx-taskq-py` 或
  `ghcr.io/kuotunyu/coding-agent-eval-fx-ledger-ts`。
- `prepared_image_tag`：方便 build 與人類辨識的 mutable alias；不作為 identity，也不進入
  fingerprint。
- `prepared_image_manifest_digest`：registry 回傳的 OCI manifest digest；immutable pull reference
  為 `<repository>@<manifest_digest>`。
- `prepared_image_config_digest`：`docker image inspect --format '{{.Id}}'` 回傳的 local image ID。

`base_image_digest` 保持 registry manifest digest。`environment.fingerprint` 改為對以下 canonical
components 計算 SHA-256：

```text
base_image_digest
prepared_image_manifest_digest
prepared_image_config_digest
os_release_id
os_release_version_id
primary_runtime_version
package_manager_version
lock_manifest_sha256
arch
```

Repository 名稱與 tag 不進入 fingerprint；相同 OCI object 即使被 mirror 到另一個 repository，仍是
同一個 execution environment。

### Fixture 與 trace versioning

- `fx-taskq-py` 從 `1.0.3` bump 至 `1.0.4`。
- `fx-ledger-ts` 從 `1.0.2` bump 至 `1.0.3`。
- Tree bytes、bugs 與 patches 不因 environment-only bump 改變；G3 仍須證明這點。
- Task registry、synthetic baselines 與所有 fixture-version references 一併更新。
- 新 run header 同時記錄 `image_ref`、`image_manifest_digest` 與
  `image_config_digest`；`tool_backend` 使用
  `measure_container:<image_manifest_digest>`。
- Trace schema bump 至 `0.2.0`。舊 traces 維持原 bytes 並繼續被明確分類為 legacy；不得靜默
  upgrade。

### Re-pin flow

1. 使用 manifest 已固定的 base digest 與 committed Dockerfile/lock manifest build
   `linux/amd64` candidate。
2. 執行完整 clean suite、全部 witness cycles、sandbox tests 與 runtime probes。
3. Owner 核准 OCI external write 後，將兩個 versioned tags push 至 GHCR；不得使用 `latest` 作為
   release identity。
4. 從 registry 讀回 manifest digest，再以 digest-qualified reference pull。
5. 驗證 pulled manifest digest、local config digest、architecture、runtime、package manager 與 lock
   hash；計算新 fingerprint。
6. 將 verified values 寫入 fixture manifests，重新執行全部 gates。

`cae fixture environment` 必須分別報告 manifest digest 與 config digest。只存在 local tag、只能
inspect config digest、registry reference 不可 anonymous pull，三種情況都不得通過 publication
gate。

## Architecture B：dual blinded adjudication

### Evidence layout

每個 current-contract mutated run 使用獨立 review set：

```text
ledger/review-sets/<review_set_id>/manifest.json
ledger/review-sets/<review_set_id>/primary.jsonl
ledger/review-sets/<review_set_id>/independent.jsonl
ledger/review-sets/<review_set_id>/resolutions.jsonl
```

`manifest.json` 綁定：

- review-set schema/protocol version；
- run ID、fixture ID/version、tree checksum；
- `findings.json` SHA-256 與 candidate-set SHA-256；
- `primary` 與 `independent` reviewer 的 public 或 pseudonymous ID；
- 每位 reviewer 相對於 fixture author 的 independence attestation；
- optional resolver ID 與 resolution ledger path。

Reviewer IDs 必須互異。v0.1 允許 fixture author `kuotunyu` 擔任 primary reviewer，但
`independent` reviewer 必須聲明未參與 fixture、mutation、agent run 或 first review。Resolver 必須
與兩位 reviewers 不同，且未參與 fixture 或 run。

### Independent review flow

1. `cae evaluate init` 從 immutable run evidence 建立 review-set manifest，並凍結 candidate-set
   hash。
2. `cae evaluate export --slot primary` 與 `--slot independent` 分別產生不同 shuffle order 的
   worksheet 與 private keymap。
3. Worksheet 不含 provider、model、adapter、budget、cost、tokens、latency、run ID、bug/finding
   IDs、另一位 reviewer 的 decision 或 identity。
4. 每位 human 獨立填寫 `DECISION` 與單行 `RATIONALE`。AI 只能建立空白 worksheet 與驗證格式，
   不得建議、代填或改寫 decision/rationale。
5. `cae evaluate import --slot ...` 只寫入該 slot 的 append-only ledger，並驗證 imported
   adjudicator ID 與 manifest 一致。

每個 slot 仍維持「每個 candidate key 最多一筆 ruling」。同一 key 可以各出現在 primary 與
independent ledgers 一次，不能在同一 ledger 重複。

### Consensus 與 disagreement protocol

Evaluator 不建立新的 human ruling，而是在記憶體中 deterministic resolve：

- 兩位 reviewers decision 相同：resolved decision 即該值，兩份原始 rationale 都保留為
  provenance。
- Decision 不同：該 pair 為 `unresolved`，不得輸出 `verified_*` headline。
- 只有 disagreement pairs 會進入 blinded resolver worksheet。Resolver 可看到原始 blinded
  excerpt、claim/root cause/evidence，以及匿名化的兩個 decisions/rationales；看不到 model 與
  reviewer identity。
- Resolver 的 human decision 寫入 `resolutions.jsonl`。Resolver 不得是 primary、independent、
  fixture author或 run operator。
- Resolution 缺漏、key/hash 不符或 resolver 身分衝突，一律 fail closed。

Formal result 的 `publishable` 不能再只由「ledger 不是 synthetic」推導。它必須同時符合：

1. candidate-set 與 run evidence hash 相符；
2. primary 與 independent coverage 都是 100%；
3. 至少一位 reviewer independent of fixture author，且兩位 reviewers 互異；
4. 所有 disagreements 都有合格 resolver；
5. 所有 entry hashes 與 protocol versions 有效；
6. 使用 current trace/environment contract。

Legacy `--ledger ledger/adjudications.jsonl` replay 仍可供歷史分析，但固定為
`publishable: false`，reason 為 `single_adjudicator_legacy`。

## Architecture C：current-contract reference suite

### Pre-registration

正式 provider call 前先提交 immutable suite registration。Registration 固定：

- v0.1 task registry 的全部 10 tasks：2 個 clean controls 與 8 個 mutations；
- provider、model、adapter/version、system prompt version、seed 與所有 generation parameters；
- 四種 budgets：tokens、tool calls、wall-clock、estimated USD；
- exact OCI manifest/config digests 與 environment fingerprints；
- task order、provider-error handling 與 retry policy；
- primary metric/reporting policy。

不得只挑成功 run 或有 matching finding 的 mutation。Provider error、timeout 與 budget exhaustion
都是 suite outcome，必須保留。Manual retry 只能依 registration 事先宣告的規則建立新 run ID，原
attempt 不得覆寫。

### Execution

- 每個 task 都使用 digest-qualified measure container；不得用 `host_process` 作為 publication
  evidence。
- Private raw events 先落 `.run-store/`，public artifacts 只由 fail-closed sanitizer 產生。
- 每個 trace 必須有 `run_header`、逐 call usage/latency、aggregate cost 與 termination，並通過
  strict replay。
- Clean controls 的 findings 全部計入 unsupported findings，不進 human bug matching。
- 八個 mutated runs 的 candidate pairs 全部進 dual blinded adjudication；沒有 candidate 的 run
  仍是完整 outcome，不得以另一個 successful run 取代。
- Suite 只產生單一 model/config 的 independently verified reference result。它不是比較、排名或
  general capability estimate。

Provider call 是 paid external action。Implementation 可完成 registration、dry-run、redacted
configuration report 與最大成本上限檢查；實際 call 必須等 owner 看過精確 model、task count 與
budget 後另行授權。

## Release audit 與 publication gates

Read-only default audit 必須驗證本機 contracts；online audit 額外驗證公開 artifacts：

- 兩個 GHCR digest-qualified references 可 anonymous pull，且 manifest/config digests 匹配；
- 10-task registration 與 run set 完整，沒有選擇性遺漏；
- public traces strict replay，cost、latency、timeout、backend 與 termination metadata 完整；
- dual review coverage 完整且 disagreement 全數 resolved；
- derived result 的 input hashes、fixture versions 與 registry 一致；
- README、Benchmark Card、Data Card、CITATION、Zenodo metadata 與 manifest claims 相符；
- public Git history 的 author/committer 只有 `kuotunyu`，沒有 co-author trailers；
- private raw store、keymaps、secrets、build cache 與 local-only tags 沒有進入 tracked/release files。

Release audit 完全通過仍不等於授權。以下 external writes 分別需要 owner 明確核准：

1. GHCR push；
2. paid provider suite；
3. source/tag/GitHub Release；
4. Zenodo upload/publish。

## Error handling

- OCI manifest/config digest、fingerprint 或 runtime component 任一 mismatch：fixture gate fail，禁止
  run。
- Anonymous pull 不可用：P6 保持 blocked。
- Sanitizer 或 strict replay 失敗：該 run 不得進 review set。
- Worksheet/keymap/hash/identity 不符：import 原子性失敗，不寫任何 ruling。
- Review coverage 不完整或 disagreement 未解：不寫 `results.json` headline。
- Clean control 發現真實 fixture defect：停止 suite，修 fixture、bump version、重新走 OCI pin 與
  registration；不得列入 unsupported finding 後繼續。
- Provider error：保留 evidence 並依 pre-registered retry policy 處理；不得刪除或覆寫。

## Testing strategy

### Unit 與 schema tests

- Manifest schema 拒絕缺少 manifest/config digest、floating release identity 或欄位混用。
- Fingerprint 對任一 digest/component mutation 都改變。
- Review-set loader 拒絕 duplicate reviewer、fixture-author independence 偽裝、hash drift、partial
  coverage 與 invalid resolver。
- Agreement、disagreement、insufficient、missing resolution 與 resolved disagreement 各有獨立
  TDD case。
- Single-ledger formal replay 明確為 legacy/unpublishable；synthetic separation 保持不變。
- Existing `ledger/adjudications.jsonl` bytes 與 hashes 不變。

### Integration tests

- Docker integration 分別觀察 registry manifest digest 與 local config digest，證明兩者不被當作
  同一值。
- Digest-qualified container 維持 `--network none`、`--read-only`、`--cap-drop ALL`、沒有 host
  bind mount。
- 兩份不同 shuffle worksheets round-trip 後產生完整 agreement set。
- 人為製造 disagreement 時 evaluator fail closed；第三份 resolver import 後才可 replay。
- 10-task scripted surrogate 驗證 registration completeness 與 provider failure retention，CI 不使用
  provider secret。

### Final verification

- Ruff、format、strict mypy、non-Docker pytest、完整 Docker matrix、G1–G11 與 package build 全過。
- Native Linux 與 Windows quality jobs 全過。
- Release artifact audit 只保留已明確允許的 historical legacy warnings。
- Online audit 在公開 GHCR artifacts 上通過後，P6 才可由 BLOCKED 改為 PASS。

## Acceptance criteria

v0.1 publication evidence phase 完成，必須同時滿足：

1. 兩個 fixture manifests 使用分離且已驗證的 OCI manifest/config digests。
2. 兩個 exact GHCR image references 可 anonymous pull，並完成全部 fixture/sandbox gates。
3. 10-task suite 已 pre-register 並使用相同 model/config 與 final environment identity 執行。
4. 每個 run 都是 current trace contract、strict replayable，且有完整 cost/latency/termination
   metadata。
5. 全部 candidate pairs 有兩份獨立 human rulings；所有 disagreements 已由第三位 human resolve。
6. Evaluator 可從 frozen evidence deterministic replay 唯一結果，且 `publishable: true` 的理由來自
   dual-review set，而不是單一 formal ledger。
7. Claims 仍限於一個 model/config、兩個 fixtures、八個 mutations，不做 ranking。
8. Release audit、CI、package build 與 contributor provenance 全部通過。
9. GitHub Release 與 Zenodo仍保持未發布，直到 owner 在看到上述 evidence 後另行核准。

## v0.2 邊界

v0.2 才處理 corpus breadth、更多 languages/repositories、更多 independent clean-tree audits、複數
models/configurations、repeated trials 與 statistical reporting。v0.2 的規模門檻與 sampling policy
必須在 v0.1 publication evidence 完成後另寫 spec，不在本階段臨時決定。
